# Documentation and decisions

Read when updating canonical docs, interfaces, behavior, deployment, data contracts, or architecture.

When implementation changes an interface, behavior, deployment requirement, data contract, or architecture decision, update the relevant documentation in the same change. Use an ADR for consequential decisions, including context, decision, alternatives, consequences, and status (`proposed`, `accepted`, or `superseded`). Do not mark a proposal accepted without user approval.

Avoid duplicating long architecture descriptions. If canonical documentation is missing, identify the document to create and distinguish proposals from settled design. Use `PROGRESS.md` for work status and `DECISION.md` for concise decisions; ADRs and contracts remain the detailed sources of truth.
